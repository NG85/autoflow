提交：

- `aafc8b9d` 作者可以编辑自己的跟进评论

## 1. 这次发版做什么

已登录用户可以修改自己写在拜访记录或周跟进实体上的评论正文。改完后向原来的收件人再发一条文本消息，正文是改后的内容，首行末尾标出编辑时间。

不能改别人的评论，不能删除，也不能改作者、回复关系、类型和创建时间。

## 2. 怎么编辑

两个写接口的地址不变。请求体仍是本次要处理的条目，不必带上整段历史。

- 不带 `id`，或 `id` 对不上已有条目：追加，和原来一样。
- 带上已有条目的 `id`，且该条 `author_id` 是当前用户：只更新 `content`，并记下 `updated_at`。
- `author_id` 不是当前用户：400，本次请求不落库。
- 目标条目是别人写的：400，文案为「只能编辑本人的评论」，本次请求不落库。

`type=comment` 的新评论仍由服务端生成 `id`。`type=task` 的新条目仍可由前端传入 `id`，不传则保持为空。

同一次请求可以既追加又编辑。其中任一条校验失败时，整次不保存。

## 3. 拜访记录

`POST /crm/visit_records/{record_id}/comments`。

能看到这条拜访的人才能写，权限与原来的追加相同。记录不存在或无权限返回 404。

`reply_to_id` 只在追加回复时校验：必须指向已有的 `type=comment`。编辑不会改这条评论原来的回复关系。

推送仍只针对 `type=comment`。顶层评论推给记录人，回复推给被回复评论的作者。收件人是自己，或收件人无效时不推。`type=task` 不推。推送失败不影响已保存的评论。

编辑后的新消息：

```
张三评论了你的跟进记录（10-23 16:04 编辑过）
[客户名  商机名](跳转链接)
评论：修改后的正文
```

回复的首行是「张三回复了你的评论（10-23 16:04 编辑过）」，第三行以「回复：」开头。时间是北京时间的月-日 时:分。新评论的文案不带这段标记。

这是再发一条飞书文本消息，不会改掉上一条气泡。

查询拜访列表和详情时，`comments` 仍是原来的 JSON。被编辑过的条目多一个 `updated_at`。没有这个字段就是没编辑过。

## 4. 周跟进

`POST /crm/weekly-followup/entities/{entity_id}/comments`。实体不存在返回 404。

编辑规则、权限口径和「只能改本人」与拜访记录相同。顶层评论推给该实体的负责人，回复推给被回复评论的作者。自己给自己不推，`type=task` 不推。

编辑后的新消息：

```
张三评论了你的周跟进总结（2026-10-20~2026-10-26）（10-23 16:04 编辑过）
[客户名  商机名](跳转链接)
评论：修改后的正文
```

回复的首行是「张三回复了你的评论（10-23 16:04 编辑过）」，中间仍有一行「周总结（起止日期）」。

负责人评论参与时间只在本次确实追加了新条目时更新。只编辑、没有新评论时不更新。

周跟进查询和保存后的返回里，评论走同一套组装。有 `updated_at` 才返回这个字段，未编辑的评论不带它。其余字段与原来相同。

## 5. 任务条目

`type=task` 和评论存在同一个 `comments` 数组里。本人再次提交一个已经存在的任务 `id` 时，更新该任务正文并写入 `updated_at`，不再返回「任务 id 已存在」。不推送。

不带 `id`，或 `id` 没出现过：仍是追加。提交别人的任务 `id`：400，整次不落库。

## 6. 验收

- 不带 `id` 的新评论、新回复，保存结果和推送对象与改前一致，文案没有「编辑过」。
- 带上本人评论的 `id` 后，只变正文和 `updated_at`。作者、回复关系、类型、创建时间不变。
- 编辑成功后，原收件人收到一条新消息，里面是改后的正文，首行末尾有编辑时间。
- 改别人的评论或 `author_id` 不是自己时返回 400，库内评论不变。
- 拜访查询能看到有值的 `updated_at`。周跟进查询只在有值时返回该字段。
- 只编辑周跟进评论时，负责人的评论参与时间不变。
- 今日重点评论仍不能编辑。
